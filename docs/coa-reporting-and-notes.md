# Reviewed COA reporting and Notes

Status: this COA reporting/Notes increment is accepted. The full FCMS module/export goal remains active.

Reporting setup belongs to the existing chart-of-accounts record. A setup actor proposes a reasoned, immutable revision; a different reviewer approves or rejects it. The maker may cancel a pending proposal. Replacements retire the previous approved revision atomically and retain the original review evidence. Existing FCMS account creation/lifecycle, book/cutover, journal review/posting and source-coverage rules are unchanged.

Unapproved, rejected and cancelled proposals are visible only to their maker and reviewers; account readers can inspect published approved/retired definitions. Setup actors can see that another proposal blocks replacement without reading its contents. Authorization is checked in application services and proposal reads are scoped in SQL. History is filtered/sorted/paged on the server.

Only actual level-two Asset/Liability groups accept current/non-current reporting sections. No treatment is inferred or seeded from codes or names. Actual level-three parent IDs supply report lines. Notes inherit from posting account to family, subgroup and root using approved definitions only: blank inherits, zero explicitly suppresses, 1–999 selects a numbered note. A narrative belongs to its explicit numbered definition and does not migrate to a different inherited number. Every participating approved ancestor/leaf revision ID is retained in report provenance.

Income and position group the exact FCMS figures by actual family. Unclassified balances remain visible. Notes use the original five-column portrait paper, ordered note numbers, account-level amounts, deduplicated narratives and totals; income/expense notes use selected-period movement and balance-sheet notes use closing amounts. Unavailable prior history remains distinct from zero. Authorized group/section/account/transaction drills retain selected dates.

V24 adds reporting metadata, constraints/triggers, partial current/pending uniqueness, bounded history indexing and an approved inheritance projection. It does not alter monetary tables. Short service transactions lock the account consistently, enforce account/base/revision versions and request idempotency, and include audit writes. A failure writing the approval audit rolls back both approval and retirement. The report snapshot uses repeatable read and one bounded mapping projection rather than per-account metadata queries. No new dependencies, application executors, cache or throughput claim.
